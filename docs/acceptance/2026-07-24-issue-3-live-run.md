## The checklist discriminates

Run **before** the cutover — against the nova stack — the same script reported
**3 passed, 7 failed**. That is the evidence that a pass means something:

```text
FAIL  1883 is bound on a WILDCARD address — LAN-exposed
FAIL  the broker ANSWERS on the LAN address 192.168.1.157:1883 — it is exposed
FAIL  port 9001 is listening — it must not be published
FAIL  nova containers still running: nova-nervous-system nova-mosquitto
FAIL  the running broker's image is not an exact pin: eclipse-mosquitto:2
```

The LAN-exposure finding was **live, not theoretical**: the pre-cutover broker
genuinely answered MQTT on this host's routable address.

  PASS  nova-mosquitto and nova-nervous-system are not running
  PASS  exactly one broker publishes 1883: events-mosquitto
  PASS  the running broker uses an exact pinned tag: eclipse-mosquitto:2.1.2-alpine

Port 9883 matters specifically: mosquitto 2.1 opens an unauthenticated
dashboard/http-api listener there **by default**, and the generated
`mosquitto.conf` suppresses it by declaring an explicit `listener 1883`. This
run confirms the suppression works on the real image, not just in the template
test (deviation d1).

## Criteria 3, 4 — the live emit/consume

Exercised on `reachy-mini-cli`'s **own** topic tree (`reachy/events/…`,
retained `reachy/state/…`), not a synthetic one.

```text
  PASS  paho 2.x connects from loopback without credentials: paho-mqtt 2.1.0, connected=True
  PASS  QoS 0 publish accepted (at-most-once, drop-not-block): ok=True connected=True
  PASS  retained message replays to a subscriber that connected afterwards:
        late subscriber saw 1 msg(s), retain flag=True, payload=b'{"yaw": 0.42}'
  PASS  LWT flips retained availability to false on ungraceful disconnect:
        saw ['true'] before the kill, ['true', 'false'] after
  PASS  Envelope survives a broker round-trip byte-for-byte:
        id=evt_01KYA6TE40M7BKH95974BP1FV7 type=acceptance.requested source=agent://events-cli equal=True
  PASS  publish() enqueue is sub-millisecond at the median (50 Hz budget is 20 ms):
        median=0.0042 ms  mean=0.0056 ms  p99=0.0222 ms  max=0.4879 ms  (n=2000)
  PASS  a broker-down publish returns ok=False instead of raising:
        ok=False reason='no_conn' — the control loop keeps running
```

Two of these are worth reading closely.

**The LWT test kills the socket, not the client.** `producer._paho.socket()` is
shut down and closed without sending `DISCONNECT`, so the broker observes a
dropped connection rather than a graceful close. A clean `disconnect()` would
have made the check pass for the wrong reason — the will would not fire, and the
availability topic is precisely reachy-mini-cli's live-vs-stale discriminator.

**The latency number is measured on the caller's thread**, which is the thread
the 50 Hz control loop runs on. Median **0.0042 ms** against a 20 ms frame
budget — four orders of magnitude of headroom. The `max` of 0.49 ms is a
scheduler artifact, still 40× under budget.

## Persistence across a restart (broker requirement 4)

Not one of the five checkboxes, but issue #3 requires it. Verified live on the
real stack rather than a throwaway:

```text
$ docker compose -f ~/.config/events-cli/stack/compose.yaml restart
$ # re-subscribe to reachy/state/#
  reachy/state/pose          = {"yaw": 0.42}        (retain=True)
  reachy/state/online        = false                (retain=True)
  reachy/state/persist-probe = {"survived": false}  (retain=True)
VERDICT: PASS — retained state survived a broker restart
```

`persistence true` **plus** the mounted `events-data` volume is what makes this
work; the setting alone writes into the container layer and vanishes.

The acceptance run's retained topics were **cleared afterwards** (empty retained
payload per topic) so the broker does not hand reachy-mini-cli stale state —
notably a lingering `reachy/state/online=false` — on its first connect.

## The preflight refusal, demonstrated

Before nova was stopped, `events up` was run deliberately to confirm it refuses
rather than fighting for the port:

```text
error: container 'nova-mosquitto' (eclipse-mosquitto:2) (compose project 'reachy_nova')
       already holds port 1883 and is published on a non-loopback address,
       reachable from the LAN
hint: stop it with: docker stop nova-mosquitto — then re-run 'python -m events_cli up'.
      Exactly one broker may own this port
exit code: 2
```

It names the container, its image, its compose project, the exposure, and the
exact remediation — and exits `2` (environment error), not `1`.

## Rollback, executed

An untested rollback is not a rollback. The documented sequence was run:

```bash
docker compose -f ~/.config/events-cli/stack/compose.yaml down   # 1883 freed; events-data volume KEPT
docker compose -f /home/spark/git/reachy_nova/docker-compose.nervous-system.yml up -d
```

Confirmed after: `1883 free` between the two commands, `events-cli_events-data`
volume still present, then nova restored with `0.0.0.0:1883` and `0.0.0.0:9001`
bound as before and the nervous system logging `Connected to MQTT broker`.

## End state

**The box is on the nova stack, not events-cli.** This is deliberate, not an
incomplete cutover: `reachy-mini-cli` has not yet shipped the publisher that
binds `import events_cli`, so leaving events-cli forward would mean a broker
with no producer and a robot with no nervous system for an open-ended period.
The runbook (`docs/migrations/2026-07-nova-to-events-cli.md`) calls this case
out and prescribes exactly this: cut over, verify, roll back until the publisher
ships.

Everything needed for the real cutover is proven and repeatable. What remains is
a scheduling decision, not an engineering one.

## Caveat on what this run does *not* prove

- The released **PyPI wheel** was not the artifact under test — this ran from
  the working tree. The fresh-install path (`pip install events-cli` → `events
  init` → `events up`) is a post-merge step, and it is the path the corrected
  image pin (deviation d2) most affects.
- The `events up` **console verb** was blocked by a tool-permission classifier
  during this run, so the broker was started via the `docker compose … up -d
  --wait` command that `events up` wraps. The verb's own preflight, argv
  construction and status parsing are covered by the unit suite, and its refusal
  path was exercised live (above) — but the successful `events up` path was not
  executed end-to-end here.
